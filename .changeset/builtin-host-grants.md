feat: a builtin task declares what it needs as its `task.grants` (`BuiltinTaskGrants` in `@fuzdev/gro/builtin_host.ts`: the fs paths, env names, and programs it reaches and the builtins it invokes), which the summaries genfile emits as `GRO_BUILTIN_TASK_GRANTS`, and takes its handles from the `host` of its `BuiltinTaskContext`, cut by them from the root's `BuiltinHostRoot`, so it imports no host module: `env` narrowed, `programs` with `program` and `find` for the granted programs, and its own frozen `raw_rest_args`; `check` and `release` do, their bodies `run_check` and `run_release` over `CheckDeps` and `ReleaseDeps`, and a project task's context has no `host`

**breaking** `InvokeTaskOptions` takes a required `host_root`, the root's `env` and `spawn` (the CLI's from the host modules), passed to nested tasks as `fs_paths` is, and `invoke_cli` takes it as a new last parameter. `RunTaskOptions` takes `host_root` and `grants`, `null` for a project task. `BuiltinTaskEntry` has `grants`, and `task_registry_render_builtins` writes the table beside the summaries. `check.task.ts` and `release.task.ts` export `task` as a `BuiltinTask`, whose `run` needs the `host`, so call `run_check` or `run_release` with plain objects rather than `task.run` with a `TaskContext`, or invoke the builtin with `invoke_task`. A builtin runs only by its name: a task with `grants` run by path, like `gro task src/lib/check.task.ts`, or re-exported from a project task file, fails with a `TaskError` naming the builtin to run instead. `gro check` reads the forwarded args it checks for a `gro test` or `vitest` section from what `invoke_task` was given, where it re-read the process's args, and importing `check.task.ts` no longer reads the working directory.
