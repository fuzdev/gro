feat: the CLI's body is `gro_main(deps: GroMainDeps)` in `@fuzdev/gro/gro_main.ts`, a module a root of the CLI calls with what it opened, `{args, fs_paths, host_root, import_module, platform}`, with `log_cli_error(error, label)` and `to_exit_code(error)` for what it throws; `invoke.ts` is the Node root that calls it. Builtins load by name from the literal imports of the generated `GRO_BUILTIN_TASK_IMPORTS` (`@fuzdev/gro/gro_builtin_task_imports.ts`, typed `BuiltinTaskImports`), which `invoke_task` imports, and the root hands every task's run a `GroPlatform` (`invoke_task.ts`), what differs between the Node Gro and the binary: the module graph's factory (`CreateModuleGraph`, `ModuleGraphOptions` in `module_graph.ts`), the Svelte config's loader, and the running Gro, a `GroPackage` (`package_json.ts`: `version` and package `dir`), which every task's context has as `gro`, and `cli_name`, the name the CLI runs as, which the builtins' listing's usage lines name. Gro's genfiles and the modules the check commands reach import no `node:` builtin: paths are text through `posix_path.ts` (with `to_file_url`, `pathToFileURL`'s reading), globs go through Gro's own matcher, and the build cache config is hashed through the blake3 host module.

**breaking** `InvokeTaskOptions`, `RunTaskOptions`, and `invoke_cli` require the root's `platform`, and `TaskContext` requires `gro`, so a hand-built context or a test calling `invoke_task` passes it. `log_builtin_tasks(log, cli_name)` takes the name its usage lines give. `to_builtin_task_id` is removed: a builtin's `resolve_task` result and its `TaskModuleMeta` have `id: null`, loaded with `load_builtin_task(name, builtin_tasks)`. `gro_paths`, `is_gro_id`, and `to_gro_package_dir` are removed from `paths.ts`, and `to_root_path` and `print_path` read every path against the given root, Gro's own files included. `package_json_load_for_gro` is removed: read `TaskContext`'s `gro.version`. `load_build_cache_dependencies(fs_paths, gro_version, runtime_version)` takes the running Gro's version, `gro_package_versions_load(fs_paths, gro_dir, names)` requires `gro_dir`, as does `install_with_cache_healing_or_throw` with `throw_if_gro_packages_changed`, `run_sync`'s options take `gro_dir`, and `task_registry_find_builtins(src_lib, import_module, root)` the root its failures are named against. `to_forwarded_args_by_command(raw_rest_args, fs_paths)` and `to_forwarded_args(command, raw_rest_args, fs_paths)` are async and take an `FsPaths` in place of the root, as do the task-path hints, which stat through it. `gro format`'s patterns, `format_directory`'s `patterns` and `root`, resolve against the project of the `FsPaths` (the CLI's working directory) rather than the process's, and a glob using an extended glob (`+(a|b)`), a brace sequence (`{1..3}`), a brace group inside another (`{a,{b,c}}`), unbalanced braces (`{a,b` or `a}`), `${`, a POSIX class (`[[:alpha:]]`), or a `..` segment, written with a backslash, as `a\..\*`, or left by a brace expansion, as `src/{..,lib}/*.ts`, fails naming it rather than matching, so none matches less than Node's `matchesGlob` did; Gro's globs take only flat brace groups. Only a glob's segments after its leading literal directory are glob syntax, so braces or brackets in the project's path or that directory's name are never read as a glob, and a glob whose `..` climbs above that directory, as `src/*/../../x/*.ts` does, fails saying so, where it matched nothing before. `NodeModuleGraphOptions` is `ModuleGraphOptions` in `module_graph.ts`. `resolve_task(fs_paths, task_name)` takes no `root`, resolving against the project of `fs_paths`. A glob whose class range is out of order (`[z-a]`) fails naming it, as does one whose brace or `(` sits inside a character class, like `[{]a` or `[!(]a`, as "a brace or `(` inside a character class", and a refusal names the pattern as written. Globs match case-sensitively on every OS, as `matchesGlob` does on Linux: a name the filesystem resolves, a pattern naming a file or a glob's leading literal directories, still matches in any case the filesystem accepts, but a wildcard or a literal segment after one matches exactly, so on macOS a quoted wildcard that relied on another case, like `'src/**/*.TS'` for `a.ts`, is spelled as on disk.
