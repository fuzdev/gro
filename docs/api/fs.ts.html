fs.ts

The fs host module: filesystem access through directory handles.

Code reaches the filesystem only through an FsDir (or the read-only FsReadDir), a handle on one directory that resolves relative paths beneath it, the shape of cap-std and WASI preopens. The import is the capability, and handing a narrower handle (dir.dir('sub'), dir.readonly()) down the call graph is how authority narrows. fs.project is the project directory, fs.open_dir opens any other directory, and fs.temp_dir makes a fresh one that removes itself on await using. Only fs and other handles make handles, and handles and their prototypes are frozen, so a handle's constructor makes nothing and no holder can patch another's ops. Each op reads its handle's state from private fields, never path, so an op called on any other object throws TypeError.

Paths beneath a handle are relative and /-separated, and resolve as openat2 with RESOLVE_BENEATH does. An absolute path, or one whose .. segments climb above the handle, fails with outside_root. So does an absolute symlink, and a relative one whose target climbs above the handle, even when it would land back inside (../root/real). The path's own .. segments resolve lexically, before any symlink, so link/.. is the handle's own directory whatever link points at; the runtime's native op resolves them the same way before calling the kernel. A trailing / means a directory, as in the kernel: stat('a.txt/') and read('a.txt/') fail with not_a_directory, write('new.txt/') fails, and remove and rename refuse a symlink named with a trailing / (not_a_directory), never acting on its target. remove and rename refuse the handle's own directory with io_error. Symlink targets, real paths, and listed names are read as bytes, and one that isn't UTF-8 fails with io_error, since no string names what the kernel would reach.

Errors are typed: each op throws an FsError (fs_error.ts) whose kind names the failure, and is_fs_error recognizes one from any copy of Gro. Each op's one expected failure returns a value instead of throwing: stat returns null on not_found, exists returns false, read_if_exists and read_text_if_exists return null, remove({missing_ok}) and mkdir({exists_ok}) return normally, and write({create_new}) returns 'exists'. Every other kind still throws, so a permission or I/O error is never mistaken for a missing file.

This is the Node implementation, which runs on the Node Gro. Its gaps against the runtime's builtin, which it documents rather than the API weakening to match:

  • Confinement is a check, then an open: the path is walked beneath the handle's directory one component at a time, reading each symlink, then the op runs on the path the walk found. A symlink swapped in between escapes, since Node has no openat2. The twin is a review signal, not a boundary.
  • A handle is bound to its directory's path, not its inode: a handle whose directory is moved or replaced follows the path, refused only when the path's real location changed (outside_root) or is gone (not_found). The runtime's handle holds a descriptor and keeps the directory it opened.
  • Intrinsics stay pollutable: code that patches String.prototype, Array.prototype, or Promise after this module loads runs inside its ops. The walk refuses a segment holding a /, so a forged segment can't climb out, and the Node functions it calls are copied at load, so syncBuiltinESMExports can't rebind them.
  • A handle opened on /proc follows its magic links, which the kernel resolves without a path the walk can check.
  • fs.open_dir takes any absolute path, checked against no grant.
  • Any module can import node:fs, so a narrowed handle bounds only code that uses the handles.
  • fs.project is the working directory when this module loads, the same source as Gro's paths.root; getcwd returns a path with symlinks resolved. Importing the module throws when the working directory has been removed, or when its path isn't UTF-8, which Node would report lossily as a different path.
